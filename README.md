# Ad Platform — Go + Python

Это Ad Platform — проект, в котором я реализовал backend-архитектуру с нуля. Я сделал систему, которая управляет рекламными кампаниями, показывает аналитику и при этом является надёжной и масштабируемой. Для этого я разбил всё на отдельные сервисы, каждый из которых отвечает за свою задачу.

**Кратко о сервисах:**
- `auth-api` (Python/FastAPI) — пользователи, аутентификация, балансы, финансовые транзакции
- `ads-api` (Go/Gin) — управление и реальная выдача объявлений
- `analytics-api` (Python/FastAPI) — хранение и анализ статистики в ClickHouse
- `worker-go` и `worker-py` — асинхронная обработка событий из RabbitMQ
- `apps/mobile` (Flutter) — мобильный кабинет для Android и iOS

**Что я также реализовал в проекте:**
- Разделил OLTP (транзакции, пользователи, балансы) и OLAP (аналитика, статистика)
- Настроил асинхронную обработку событий через RabbitMQ
- Реализовал финансовые операции с гарантиями ACID (в auth-api)
- Добавил инфраструктуру для кэширования в Tarantool
- Настроил мониторинг через Prometheus и Grafana
- Настроил развёртывание через Ansible
---

## 🧱 Архитектура проекта

Я организовал проект как моно-репозиторий, внутри которого находятся несколько микросервисов. Это удобно: весь код в одном месте, но при этом сервисы независимы и могут разрабатываться отдельно.

## 🔹 Роли сервисов

### `auth-api` (FastAPI, Python)

Это основной сервис для работы с пользователями и транзакциями. Я сделал его на Python с FastAPI, потому что тут много бизнес-логики и важно быстро итерироваться.

**Что я здесь реализовал:**
- Регистрация и логин пользователей
- JWT-аутентификация с токенами
- Система ролей (кто админ, кто обычный пользователь)
- Управление балансами и финансовыми транзакциями
- Миграции базы данных через Alembic

**Самое важное:** все финансовые операции я обернул в ACID-транзакции. Это значит, что деньги не могут «потеряться» — если что-то идёт не так, вся операция откатывается назад.

**База данных:** я спроектировал схему с таблицами `users`, `balances`, `transactions`, `campaigns`, `ads`, `creatives`. Все таблицы связаны через внешние ключи (FK), чтобы данные были целостными.


### `ads-api` (Go)

Этот сервис я написал на Go для работы с рекламными кампаниями и объявлениями. Go выбрал потому, что тут важна скорость и эффективность при обработке множества запросов.

**Что я здесь сделал:**
- CRUD-операции для кампаний, объявлений, креативов, площадок, рекламных мест и форматов
- Подключение к MySQL через библиотеку `sqlx`
- Разделил код на слои: handler → service → store (так проще тестировать и поддерживать)
- Отправку событий в RabbitMQ (когда объявление создаётся или обновляется)
- Выбор активного объявления по месту размещения и весу, выбор креатива и идемпотентный учёт показа
- Таргетинг объявлений по возрасту, полу, интересам, стране, региону, городу, типу устройства и операционной системе
- Общие бюджеты и дневные лимиты кампаний, CPM-ставки объявлений и расписание показов
- Загрузку изображений и видео для креативов с проверкой фактического MIME-типа и размера
- Модерацию креативов со статусами, причиной отклонения и отдельной очередью администратора
- Click tracking с JSON-ответом или HTTP redirect на целевую страницу
- Транзакционный MySQL outbox для гарантированной доставки событий показа и клика

**Важный момент:** этот сервис не владеет схемой базы данных и не делает миграции — этим занимается `auth-api`.

### Медиа-креативы

Текстовые креативы продолжают работать через `POST /creatives`. Изображение или видео загружается как `multipart/form-data`:

```bash
curl -X POST http://localhost:8080/creatives/upload \
  -F ad_id=1 \
  -F 'content=Описание баннера' \
  -F file=@banner.png
```

Поддерживаются JPEG, PNG, GIF и WebP до 10 МБ, а также MP4, WebM и MOV до 100 МБ. Сервер определяет тип по содержимому файла, присваивает безопасное имя и возвращает метаданные в поле `media`. Файл доступен по URL из `media.url`. Для замены файла используется `PUT /creatives/{id}/upload`; удаление креатива удаляет и файл.

Файлы хранятся в Docker volume `ads_media`, поэтому сохраняются при пересоздании контейнера. Выдача `/delivery/select` включает снимок поля `media`, соответствующий выбранному креативу.

### Модерация креативов

Новый или отредактированный креатив получает статус `draft`. Владелец отправляет его на проверку через `POST /creatives/{id}/submit`. После этого статус становится `pending`.

Пользователь с ролью `admin` получает очередь через `GET /moderation/creatives?status=pending` и принимает решение через `POST /moderation/creatives/{id}/review`:

```json
{
  "decision": "rejected",
  "reason": "Добавьте обязательную маркировку рекламы"
}
```

Поддерживаются решения `approved` и `rejected`; при отклонении причина обязательна. Любое редактирование сбрасывает креатив в `draft`. В рекламную выдачу попадают только креативы со статусом `approved`. Маршруты модератора проверяют JWT и permission `moderation.review`.

### Управление пользователями и Admin Workspace

`auth-api` является единым источником пользователей, ролей, permissions и сессий. Публичная регистрация всегда создаёт обычного пользователя. Отдельный Django Admin отключён: административный интерфейс находится в Flutter-приложении.

Первый `superadmin` создаётся внутри контейнера:

```bash
docker compose --env-file infra/.env -f infra/docker-compose.yml exec auth-api \
  python -m app.cli create-admin --email admin@example.com
```

Пароль вводится интерактивно и не попадает в аргументы процесса. При первом входе администратор обязан подключить TOTP MFA. Access token действует 15 минут, refresh token ротируется и хранится на сервере только в виде SHA-256-хеша.

Поддерживаются роли `user`, `moderator`, `support`, `finance_admin`, `admin` и `superadmin`. Admin API под `/admin/*` проверяет permissions, актуальную версию пользователя, серверную сессию и MFA. Блокировка сразу отзывает сессии, увеличивает `token_version`, ставит активные кампании на паузу и создаёт append-only запись аудита. Разблокировка не запускает кампании автоматически.

| Роль | Основные permissions |
| --- | --- |
| `user` | административных прав нет |
| `moderator` | `moderation.review` |
| `support` | `users.read`, `users.sessions.revoke` |
| `finance_admin` | `users.read`, `billing.read`, `billing.adjust` |
| `admin` | управление пользователями, финансами, модерацией, fraud и аудитом |
| `superadmin` | все права `admin` и `admins.invite` |

Состояние пользователя и сессии кешируется в Redis. `ads-api` сверяет `status`, `token_version` и `sid` на каждом приватном запросе; при недоступности Redis приватный запрос завершается безопасной ошибкой `503`. Событие `user.blocked` дополнительно обрабатывается `ads-api` через durable RabbitMQ-очередь.

Сброс пароля не позволяет администратору установить известный ему пароль. Admin API создаёт одноразовый токен на 30 минут, хранит только его хеш, отзывает сессии и публикует внутреннее событие `user.password_reset.requested`; новый пароль пользователь задаёт через `POST /auth/password-reset/complete`. Доставка ссылки должна выполняться доверенным почтовым consumer этого события.

Миграции управления пользователями применяются последовательно: `k1f2a3b4c5d6` (роли, permissions, сессии, приглашения и аудит) и `l2a3b4c5d6e7` (одноразовые password-reset токены).

Приватные endpoint кампаний, объявлений, креативов, площадок, финансов и аналитики используют пользователя из JWT и не доверяют переданному клиентом `user_id`. Для настройки используйте [`infra/.env.example`](infra/.env.example) с независимыми `SECRET_KEY`, `MFA_ENCRYPTION_KEY` и `INTERNAL_SERVICE_TOKEN`.

### `analytics-api` (FastAPI, Python)

Сервис для аналитики. Я сделал его отдельно, потому что аналитические запросы сильно отличаются от обычных транзакций — они читают много данных и агрегируют их.

**Что я здесь реализовал:**
- Хранение статистики по показам, кликам, конверсиям, их ценности и расходам в ClickHouse
- REST API для получения аналитики с фильтрацией по датам, кампаниям, объявлениям и креативам
- Асинхронный консьюмер для RabbitMQ — сервис подписывается на события и записывает статистику в ClickHouse

Реальные события показов, кликов и конверсий хранятся в `delivery_stats`. `event_id` и `ReplacingMergeTree` защищают аналитику от повторной доставки одного события, а API агрегирует эти данные по кампаниям, объявлениям и креативам. Для конверсий дополнительно доступны количество и суммарная ценность.

## 🎯 Выдача рекламы

Объявление участвует в выдаче, когда кампания, площадка, рекламное место, формат и само объявление имеют статус `active`, заполнен `destination_url` и есть хотя бы один креатив. `weight` задаёт относительную частоту выбора среди объявлений одного рекламного места.

У объявления можно настроить `targeting`: возрастной диапазон, пол, интересы, страны, регионы, города, типы устройств и операционные системы. Пустая группа правил не ограничивает выдачу. Если правило задано, запрос должен содержать соответствующий сигнал и совпадать с ним; для интересов достаточно пересечения хотя бы по одному значению.

Площадки управляются через `/sites`, каталог форматов — через `/formats`, рекламные места — через `/placements`. При создании места сервер выдаёт стабильный UUID в поле `code`. Объявление связывается с местом через `placement_id`, а клиент запрашивает рекламу по этому публичному коду.

Запрос объявления:

```bash
curl -X POST http://localhost:8080/delivery/select \
  -H 'Content-Type: application/json' \
  -d '{
    "request_id": "010c236c-20c1-48f9-ac13-d9b9db620845",
    "placement_code": "010c236c-20c1-48f9-ac13-d9b9db620845",
    "visitor_id": "visitor-42",
    "audience": {
      "age": 27,
      "gender": "female",
      "interests": ["travel", "sports"]
    },
    "geography": {
      "country": "RU",
      "region": "moscow",
      "city": "moscow"
    },
    "device": {
      "type": "mobile",
      "operating_system": "android"
    }
  }'
```

`request_id` можно не передавать: сервер создаст UUID. Повтор с тем же UUID возвращает ту же выдачу. В ответ входят `site_id`, `placement_id`, `format_id`, коды места и формата, размеры формата и нормализованный контекст аудитории, географии и устройства. Этот же контекст сохраняется со всеми событиями в MySQL и ClickHouse. Если подходящих объявлений нет, API отвечает `204 No Content`. Старый запрос по `placement` сохранён для объявлений без `placement_id`.

В ответе есть выбранные `ad_id` и `creative_id`, контент, медиафайл, целевая ссылка, а также `impression_url`, `click_url` и `conversion_url`. Клиент подтверждает фактическое отображение через `POST impression_url`. Для клика можно открыть `GET click_url` и получить redirect или отправить `POST click_url` и получить JSON. Клик автоматически фиксирует пропущенный показ. Показ и клик идемпотентны для одной выдачи.

Конверсия отправляется с устойчивым идентификатором события:

```bash
curl -X POST http://localhost:8080/delivery/DELIVERY_ID/conversion \
  -H 'Content-Type: application/json' \
  -d '{
    "event_id": "order-42",
    "conversion_type": "purchase",
    "value": 2499.50,
    "currency": "RUB"
  }'
```

Повтор с тем же `event_id` и теми же данными возвращает существующий результат и не увеличивает статистику. Повтор с изменённой суммой, валютой или типом отклоняется с `409 Conflict`.

### Атрибуция и антифрод

Если приложение знает только стабильный `visitor_id`, оно может отправить конверсию через `POST /attribution/conversion`. Backend найдёт последний валидный клик за 7 дней, а при его отсутствии — последний показ за 24 часа. В событии и ответе сохраняются `attribution_model` (`last_click` или `view_through`) и использованное окно атрибуции.

Антифрод блокирует выдачу известным bot/crawler-клиентам и помечает подозрительные клики или конверсии по скоростным лимитам, IP/visitor-сигналам и аномальной ценности. IP-адрес и User-Agent сохраняются только как SHA-256 хеши. Подозрительные события остаются в потоке для аудита с `fraud_reason`, но исключаются из показателей, расхода и ценности конверсий в аналитическом API. Поле `total_fraud_events` показывает количество отфильтрованных событий.

### Бюджет, ставка и расписание

Кампания принимает настройки бюджета и расписания:

```json
{
  "budget": {
    "total": 50000,
    "daily_limit": 2500
  },
  "schedule": {
    "starts_at": "2026-10-25T00:00:00Z",
    "ends_at": "2026-11-30T23:59:59Z",
    "days_of_week": [1, 2, 3, 4, 5],
    "start_hour": 8,
    "end_hour": 22
  }
}
```

`days_of_week` использует ISO-нумерацию: понедельник — `1`, воскресенье — `7`. Даты, часы и дневной лимит считаются по UTC. Пустой список дней означает ежедневный показ, интервал часов может переходить через полночь, а нулевой бюджет или дневной лимит означает отсутствие соответствующего ограничения.

У объявления поле `bid_cpm` задаёт стоимость тысячи показов. Стоимость одного показа равна `bid_cpm / 1000`; она атомарно добавляется к общему и дневному расходу кампании и передаётся в ClickHouse. Ставка вместе с `weight` влияет на вероятность выбора объявления. Кампания не участвует в выдаче вне расписания или после исчерпания любого лимита.

## ⚒️ Конфигурация через .env

Все настройки я вынес в переменные окружения. Это удобно: можно легко менять пароли, ключи и другие параметры без изменения кода.

**Как настроить:**
```bash
cd infra
cp env.example .env
```

**Что нужно задать в `.env`:**
- `MYSQL_ROOT_PASSWORD` — пароль администратора MySQL
- `MYSQL_PASSWORD` — пароль пользователя приложения
- `SECRET_KEY` — секретный ключ для JWT-токенов
- `MFA_ENCRYPTION_KEY` — отдельный ключ шифрования TOTP-секретов
- `REDIS_URL` — Redis для актуального состояния пользователей, сессий и rate limit входа
- `INTERNAL_SERVICE_TOKEN` — service-to-service ключ внутренних billing endpoint
- `GF_SECURITY_ADMIN_PASSWORD` — пароль администратора Grafana

Файл `.env` я добавил в `.gitignore`, чтобы секреты случайно не улетели в репозиторий.

## 🏎️ 🚀 🔥 Развертывание в production с Ansible

Я подготовил инфраструктуру для развёртывания на серверах с помощью Ansible. Это нужно для того, чтобы в будущем можно было автоматически настроить окружение: от установки Docker до развёртывания всех сервисов и мониторинга.

**Важный момент:** у меня нет удалённых серверов, и я не развёртывал это в production. Ansible — это задел на будущее, чтобы показать, как можно автоматизировать деплой.

Ansible использует шаблоны Jinja2 — это значит, что конфигурационные файлы генерируются автоматически на основе заданных переменных.

### 1. Установка зависимостей
```bash
cd infra/ansible
ansible-galaxy install -r requirements.yml
```

### 2. Настройка инвентаризации
Нужно отредактировать файл `inventory/production.yml` и указать IP-адреса ваших серверов.

### 3. Настройка переменных
В файле `group_vars/production.yml` я задал конфигурацию для production-окружения — тут можно указать размеры контейнеров, порты и другие параметры.

### 4. Запуск плейбука
```bash
ansible-playbook -i inventory/production.yml playbook.yml
```

### 5. Проверка развертывания
```bash
# Проверка запущенных контейнеров
ansible production -m shell -a "docker ps"

# Проверка работоспособности приложения
ansible production -m uri -a "url=http://localhost:8080/health"
```

### Что я запланировал для production

**Масштабируемость:** Ansible позволяет развернуть сервисы на нескольких серверах:
- Базы данных можно вынести на отдельные серверы
- Приложения запустить на разных хостах
- Мониторинг разместить на выделенном сервере

**Безопасность:**
- SSH-доступ к серверам
- Управление секретами через Ansible Vault
- Настройка брандмауэра
- Установка SSL/TLS сертификатов

**Производительность:**
- Оптимизация конфигурации под нагрузку
- Автоматическое масштабирование
- Выделение ресурсов под каждый сервис

**Мониторинг:**
- Prometheus собирает метрики со всех сервисов

## 📊 ClickHouse

ClickHouse я выбрал для хранения аналитики — он отлично справляется с большими объёмами данных и позволяет быстро агрегировать информацию.

**Какие таблицы я создал:**
- `ads_stats` — детальная статистика по каждому объявлению (показы, клики, стоимость)
- `campaign_stats` — агрегированные данные по кампаниям
- `creative_stats` — аналитика по креативам
- `delivery_stats` — идемпотентный поток реальных показов и кликов

Все таблицы используют движок MergeTree — он позволяет эффективно хранить данные и быстро выполнять запросы.

**Зачем это нужно:**
- Можно хранить миллионы записей о показах и кликах
- Быстро получать метрики: CTR, расходы, конверсии
- Анализировать эффективность рекламы по временным периодам

### Как я это использую:

**1. Создание базы данных и таблиц:**

Таблицы создаются автоматически при `make up`. Повторно применить
идемпотентный скрипт вручную можно так:
```bash
bash infra/scripts/create_clickhouse_db.sh
```

Или вручную через curl:
```bash

```

**2. Загрузка и анализ данных:**
Таблицы оптимизированы для хранения миллионов записей. MergeTree движок обеспечивает быструю вставку и эффективные запросы с агрегацией.

**3. Интеграция с микросервисами:**

## 🐰 RabbitMQ

RabbitMQ я использую для асинхронной обработки событий. Это позволяет сервисам не блокироваться друг на друге — например, когда создаётся объявление, событие уходит в очередь, а воркеры обрабатывают его в фоне.

**Как я настроил архитектуру:**
- **Обменник**: `ad_events` (тип topic) — маршрутизирует события
- **Очереди**: `ad_worker_queue` — воркеры забирают сообщения отсюда
- **Routing keys**: `ad.created`, `ad.updated`, `ad.impression`, `ad.click`, `ad.conversion`

**Какие сервисы интегрированы:**

### Go-сервисы (`ads-api`)
- Файл `services/ads-api/internal/service/rabbitmq.go` — сервис для работы с RabbitMQ
- События жизненного цикла объявления публикуются при создании и обновлении
- События показов, кликов и конверсий сначала атомарно сохраняются в `delivery_outbox`, затем подтверждённо публикуются в RabbitMQ фоновым dispatcher

### Python-сервисы
- `auth-api`: `services/auth-api/app/core/rabbitmq.py` — базовое подключение
- `analytics-api`: `services/analytics-api/app/core/rabbitmq.py` — асинхронный consumer для аналитики
- Воркеры: `services/workers/worker-py/worker.py` и `services/workers/worker-go/main.go` — обработка сообщений

### Как я это использую:

**1. Запуск RabbitMQ:**
```bash
# RabbitMQ доступен на порту 5672 (AMQP) и 15672 (Web UI)
# Web UI: http://localhost:15672
# Логин и пароль: RABBITMQ_DEFAULT_USER / RABBITMQ_DEFAULT_PASS из infra/.env
```

**2. Публикация событий из ads-api:**
```go
// Автоматическая публикация при создании объявления
if s.rabbitmq != nil {
    if err := s.rabbitmq.PublishAdCreated(
        ctx, fmt.Sprintf("%d", ad.ID), ad.CampaignID,
    ); err != nil {
        // Логируем ошибку, но не прерываем операцию
    }
}
```

**3. Обработка сообщений в воркерах:**
```go
// Go воркер обрабатывает сообщения из очереди
func (w *AdEventWorker) processMessage(d amqp091.Delivery) {
    var data map[string]interface{}
    json.Unmarshal(d.Body, &data)

    eventType, err := requiredString(data, "type")
    if err != nil {
        d.Nack(false, false)
        return
    }
    switch eventType {
    case "ad_created":
        w.handleAdCreated(data)
    case "ad_updated":
        w.handleAdUpdated(data)
    }
}
```

**4. Воркеры:**
- Go worker (`services/workers/worker-go/main.go`) — обрабатывает события
- Python worker (`services/workers/worker-py/worker.py`) — тоже обрабатывает события
- Оба воркера подписаны на `ad_worker_queue` и обрабатывают `ad.created` и `ad.updated`

**5. Асинхронная аналитика:**
- `analytics-api` потребляет сообщения через асинхронный consumer
- Обработка через asyncio в фоновом режиме
- API не блокируется при обработке
- События `ad.created` и `ad.updated` записываются в ClickHouse для статистики

**6. Надёжность:**
- Все сервисы корректно завершают работу (graceful shutdown)
- Обработка ошибок подключения
- Автоматическое восстановление соединений
- Подтверждение обработки сообщений (ACK/NACK)

## 🔒 ACID-транзакции

Я реализовал полную поддержку ACID-транзакций для всех финансовых операций. Это было важно, потому что деньги не должны «теряться» или «появляться из ниоткуда».

### Атомарность (Atomicity)
Все операции выполняются в рамках одной транзакции. Если что-то идёт не так — происходит автоматический rollback. Гарантирую, что либо все изменения применяются, либо ни одно.

### Согласованность (Consistency)
Я использовал внешние ключи (FK) для поддержания целостности данных. Транзакции ссылаются на созданные объявления и креативы, бизнес-правила соблюдаются на уровне базы данных.

### Изолированность (Isolation)
Для предотвращения гонок я использую `SELECT ... FOR UPDATE`. Это блокирует строки на время финансовой операции — никто не может изменить баланс, пока транзакция не завершится.

### Долговечность (Durability)
Все изменения фиксируются в базе данных и сохраняются даже при сбоях системы. Финансовая история не потеряется.

### Как я это реализовал:
- **Python (auth-api)**: SQLAlchemy транзакции с `with_for_update()` — это основной сервис для работы с транзакциями
- **Связь сущностей**: `transaction_id` в таблицах `ads` и `creatives` — связывает транзакции с объявлениями и креативами
- **API endpoints**: `/billing/deposit`, `/billing/withdraw`, `/billing/charge-for-ad`, `/billing/charge-for-creative` — всё в auth-api
- **Тестирование**: транзакции протестированы на корректность и изолированность
